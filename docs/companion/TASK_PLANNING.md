# Task-scoped dynamic plans — contract 1.4.0

The existing conversation planner remains available outside companion tasks. Companion execution binds TaskExecutionContext on the backend thread; model input cannot choose an owner or another task. New logical tools plan_create/get/add_step/update_step/reorder/complete are registered through the existing JarvisTool/ToolSchemaProvider/DefaultToolManager/native mapper architecture as taskplan__create/get/add_step/update_step/reorder/complete. Legacy plan tools reject companion-context mutations with directions to the evidence-gated tool family. Simple conversation does not need a plan; the model decides whether complex executable work needs one, without keyword routing.

A task has at most one plan; CREATE does not overwrite it. Revisions begin at 1 and increase on every accepted mutation. Changes require expectedRevision, preventing stale/duplicate requests from applying twice. Step IDs stay stable when inserting/reordering; positions are zero based. COMPLETED/SKIPPED/CANCELLED steps are immutable. A failed step may explicitly return to IN_PROGRESS while its task is active; the failed revision remains auditable, startedAt resets, and new post-retry evidence is required. Changing metadata never repeats an external action automatically. Plans support up to 100 bounded public steps and retain up to 200 immutable revisions.

DefaultToolManager issues executionEvidenceRef only while a registered owned task is active. Receipts contain tool/operation/time/success, not arguments, prompts or raw outputs. Planning calls cannot issue receipts. A COMPLETED step must have started and must cite a successful same-task/owner receipt issued after that start. Failed calls, approval requests, pending/running markers and nonzero exit codes cannot verify completion. A receipt proves observed execution success, not every semantic claim about a goal. Task descriptions/results must remain grounded. When work happened before a plan existed, use a fresh read/verification; do not repeat external writes solely to obtain a receipt. The final answer itself needs no artificial executable step.

PENDING -> IN_PROGRESS/SKIPPED/CANCELLED; IN_PROGRESS -> COMPLETED/FAILED/SKIPPED/CANCELLED; FAILED -> IN_PROGRESS only by an explicit revision-checked retry. SKIPPED needs a public reason. plan_complete checks all steps COMPLETED/SKIPPED. Task finalization independently rejects unfinished/unverified plans; a model's success text alone cannot complete a task. Cancellation/timeouts cancel unfinished plan steps and reject new tool admission; already in-flight external actions cannot be undone by this metadata mechanism.

Task/plan mutations, snapshot construction and journal publication use the same state monitor. /state and system.snapshot include plans and one atomic latestSequence. Plan events carry full legacy Task fields plus nested plan; this preserves the existing Windows task.* parser. completedStepCount/totalStepCount are counts, never elapsed-work percentages; Task.progress remains null. No private reasoning/prompts or secret-shaped labels are allowed. API_CONTRACT.md and schemas/1.4.0 define exact wire shapes.

Reference fixtures: fixtures/plan-replay.json and SHARED/fixtures/plan-replay-1.4.0.json. scripts/companion_plan_reference.py is an illustrative consumer, not the backend authority. Consumers advance sequence for every valid journal event, deduplicate eventId, ignore stale plan revisions, and request an authoritative snapshot on gaps or instance changes. Two Python tests cover duplicate/stale delivery and out-of-order gap recovery.
