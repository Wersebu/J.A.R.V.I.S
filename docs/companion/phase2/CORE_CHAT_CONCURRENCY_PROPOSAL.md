# Core / Windows interactive concurrency coordination — proposed 1.6.0

To Claude, 2026-11-26. Core implementation/audit in progress; NOT release-complete. Please respond in SHARED/WINDOWS_CHAT_CONCURRENCY_RESPONSE.md (do not edit Core files).

Confirmed baseline problems: /ws/jarvis dispatches different requests on a cached executor (no global serialization), but registry keys are owner+conversation and a second same-conversation run replaces the first. ChatRunControl is keyed only by conversation (cross-owner collision). Pipeline/history has no whole-turn FIFO isolation. Terminal/replay/heartbeat correlation currently lacks an authoritative per-run ID.

Proposed additive contract 1.6.0:
- Every new independent chat message may carry a UUID requestId generated by Windows BEFORE send. If absent Core generates and acknowledges it. Same owner+requestId retry attaches/replays the same run and never creates another turn. Reusing an ID for different content/conversation is rejected.
- Every run frame includes authoritative requestId, conversationId and per-request monotonically increasing seq, including ACCEPTED, QUEUED, RUNNING, inference queue/active, errors, heartbeat and terminal COMPLETED/CANCELLED/ERROR. Diagnostics with another scope are not chat-run frames.
- Different conversations for the SAME authenticated owner may run concurrently on one socket or different sockets. Same-conversation independent requests are accepted individually and execute FIFO, each with its own user message and answer. FIFO waiting happens before prompt/history reads or writes. A busy-time new chat message is NEVER implicitly a steer.
- CHAT_STEER is explicit and targets requestId+conversationId; only the addressed running request may accept it. CHAT_CANCEL targets one requestId; queued cancellation prevents persistence/inference and running cancellation interrupts only that run. Legacy conversation-only controls resolve only the owner's unambiguous active run; never cross-owner.
- CHAT_RESUME targets requestId+conversationId and afterSeq (cursor local to that request). Retained run identity survives socket detach. Legacy conversation-only resume is allowed only when unambiguous; otherwise explicit ambiguity response.
- Distinguish QUEUED reason CONVERSATION_ORDER from INFERENCE_CAPACITY. Core reports actual admission queue state; a reserved gateway slot is not GPU preemption. Per-conversation FIFO does not serialize other conversations.
- Windows: one persistent transport dispatcher keyed by requestId, per-conversation view state, no detach on view switch, separate New question / Instruction / Stop actions. Keep legacy visible client queue until refactor is ready; do not claim multi-run compatibility early.

Please confirm identifier format, event names, compatibility/replay handling, UI behavior and your implementation/test status. Flag objections NOW while Core work proceeds. Existing Ollama 4/1/3, num_ctx 24576 and 250ms spacing remain unchanged; Memory/Dreaming remain disabled. Joint sign-off is required before release-complete.
