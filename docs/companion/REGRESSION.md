# Scheduling regression investigation

NativeToolLoopServiceStoreAuditGovernanceTest.fullRealProductionScenarioReachesScheduledWithAllTwentyThreeRecords reproduced at baseline commit 1655d71 using a git-archive extraction under workspace test-tmp. Baseline log: companion-baseline-repro.log. Failure: expected the Polish scheduling answer, received a context-checkpoint failure. No baseline source was edited.

Cause: the fixture manually constructs NativeToolLoopService, so Spring does not inject application.yml's configured context budget. It fell back to a 16384-token window while running a large 23-store workflow. Its scripted provider also consumed the next business/tool turn when the service asked for a tool-free checkpoint summary, causing the checkpoint guard to reject that response.

Repair: configure the large workflow fixture with the same 100000/2048 context budget as the existing application configuration, and make its fake provider recognize checkpoint summarization without consuming scripted business turns. Assertions still require SCHEDULED, 23 stores and 23 uniquely scheduled IDs. No production context guard was removed or weakened; ContextBudgetTest still runs. This is a fixture/configuration correction, not a reason to increase production context settings.

Broader testing also found three GmailToolTest failures involving consent/scope and dependent listing/attachment fixtures. All three reproduced on baseline 1655d71 in the isolated archive. The happy-path fake token endpoint returned only GoogleService.GMAIL.scopes().getFirst() while production correctly requires the full configured scope set. The fixture now returns String.join(" ", GoogleService.GMAIL.scopes()); no production consent check was relaxed. Dependent list/attachment tests can then establish their test account connection. The existing context-wiring test attempted real startup inference; its HTTP client is now mocked to keep bean-wiring validation isolated. Warmup behavior remains covered by dedicated Ollama tests.
