# Durable task and plan history

The CompanionDocumentStore boundary has in-memory and SQLite implementations. Persistence is opt-in: jarvis.companion.history.enabled=false by default. Enabling it uses a separate ./data/companion-history.db unless history.path is configured. This adds a new namespaced companion_documents table in that isolated file; it does not migrate, replace or delete existing conversation memory/knowledge storage. SQLite WAL, synchronous=FULL and transactional document batches persist public task/plan state. Raw task prompts and model reasoning are not stored in task history.

An adjacent OS writer lease prevents two live backend instances from sharing/recovering the same history file. A second instance fails closed before changing history. A process crash releases the lease; SQLite recovers committed transactions on the next open. Use one backend writer per history file. Corrupt/unreadable history fails startup instead of being discarded.

At restart, terminal tasks/plans remain available with their IDs/revisions. QUEUED/RUNNING/CANCEL_REQUESTED tasks become FAILED with a restart-interruption error. Their unfinished plans become INTERRUPTED; unfinished steps become CANCELLED while already verified terminal steps remain intact. A completed task with an inconsistent unfinished plan is also failed conservatively. No job is queued again, no model/tool call is retried, and no external effect is repeated. The new serverInstanceId and fresh process-local event sequence require a complete state.sync; the event journal is not durable.

Retention: terminal history defaults to 30 days and at most 1000 retained tasks; 0 retention-days disables the age rule. Active work is never expired from history. DELETE /tasks/{id} requires ownership and a terminal task. SQLite deletes that task, plan, revisions and execution receipts atomically. Associated replay frames are scrubbed, so cursors that cross a deletion gap require a fresh snapshot. The deletion event is a legacy-shaped tombstone with result/error cleared. Deletion does not undo external actions.

Proof: tests write unfinished task/plan data in a separate JVM, recover it through a fresh store/engine without any ChatService invocation, verify owner isolation, and confirm deletion after reopening. Additional tests cover writer exclusion, retention and deadlines. Live isolated-server crash testing restored a completed revision-10 plan, reconciled an in-flight task to FAILED/INTERRUPTED with no repeated ToolManager actions, rejected the old WebSocket instance ID, and verified deletion of all related rows with a read-only SQLite query.

Only a successfully initialized/recovered persistent store reports durableHistory=true. The default backend remains false. The nonproduction integration launcher explicitly enables its own data/companion-integration/history.db after the recovery tests passed. Existing journal/snapshot semantics and 1.3.0 task fields are preserved.
