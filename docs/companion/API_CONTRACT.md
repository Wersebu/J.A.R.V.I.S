# Companion API contract 1.5.0

Updated 2026-11-25 (1.5.0; prior publication 2026-11-24). Backend owns state. Additive to existing APIs; legacy /ws/jarvis is unchanged. Version changes are recorded here and in CONTRACT_VERSION.txt. Major = incompatible; minor = additive; patch = clarification. Clients ignore unknown fields/events.

## Availability
Initial integration target: /api/v1/companion REST and /ws/companion. See CODEX_STATUS.md for verified implementation. Reserved events below are NOT capability claims. No deployment has occurred.

## Authentication
Reuse POST /api/v1/auth/login {"email":"...","password":"..."}; response {"accessToken":"...","expiresAt":"RFC3339","user":{"id":"...","email":"...","displayName":"...","role":"..."}}. Bootstrap is existing /api/v1/auth/bootstrap-status and /bootstrap; never bootstrap automatically. Send Authorization: Bearer TOKEN for REST and WebSocket upgrade; existing interceptor also supports access_token query parameter but desktop should use headers to avoid logging tokens. 401 requires login; no refresh endpoint. GET /api/v1/auth/me and POST /api/v1/auth/logout remain. HTTPS/WSS outside trusted local development. Every task, snapshot, event and command is owner-scoped; another user's ID returns 404.

## REST integration target
All paths below relative to /api/v1/companion. JSON bodies/responses, authenticated.
- GET /capabilities -> {"contractVersion":"1.5.0","tasks":true,"taskPlans":true,"planEvidenceRequired":true,"voiceStreaming":false,"durableHistory":false} (additional flags permitted).
- POST /tasks -> 202 Task. Body {"message":"Research this topic","role":"RESEARCH","priority":20,"timeoutSeconds":120,"maxAttempts":1}. Supported roles: TASK/RESEARCH (omitted role defaults to TASK). Task-queue priority 0..100, lower first, default 50; this is independent of inference-profile priority and the interactive gateway reservation. Timeout 1..3600 seconds includes queue wait. maxAttempts must be 1; no automatic retry of tool side effects. Client must not blindly retry POST: no idempotency key yet.
- GET /tasks -> array of retained Task, newest first.
- GET /tasks/{taskId} -> Task or 404.
- POST /tasks/{taskId}/cancel -> Task (200); idempotent for terminal tasks. A cancellation request is not completion. State becomes CANCEL_REQUESTED, then CANCELLED when the worker exits. Queued cancellation can become CANCELLED immediately. No promise to undo external side effects.
- GET /state -> {"contractVersion":"1.5.0","serverInstanceId":"UUID","latestSequence":0,"tasks":[Task],"plans":[Plan],"activeProcesses":0}. Count QUEUED/RUNNING/CANCEL_REQUESTED. Snapshot reflects server state; indeterminate progress is null.
- GET /events?afterSequence=0 -> {"resetRequired":false,"events":[Event],"latestSequence":0}. Polling fallback for the same stream. Out-of-range cursor returns resetRequired=true and client must replace state via /state. Sequence scoped to user and server process.

Task shape: {"taskId":"UUID","role":"TASK","state":"QUEUED","priority":50,"progress":null,"createdAt":"RFC3339","updatedAt":"RFC3339","result":null,"error":null}. Result/error are nullable strings. Message and internal prompts are not echoed in snapshots. Terminal states COMPLETED, FAILED, CANCELLED, TIMED_OUT are immutable. Transitions QUEUED -> RUNNING -> COMPLETED|FAILED; QUEUED|RUNNING -> CANCEL_REQUESTED -> CANCELLED; timeout -> TIMED_OUT only after worker exits. Timeout/cancel interrupts are cooperative; an uninterruptible worker retains its slot and CANCEL_REQUESTED state until it stops. Progress 0..100 only when measured; null means unknown. Initial handler reports null throughout.

## WebSocket
New endpoint /ws/companion. Server sends system.connected with payload {"contractVersion":"1.5.0","serverInstanceId":"UUID"}. Client command {"type":"state.sync"} -> system.snapshot payload identical to GET /state; {"type":"events.resume","afterSequence":42,"serverInstanceId":"UUID"} -> replay retained events followed by system.resumed {"latestSequence":43}; replay gap -> system.reset_required, then request snapshot. No task submission over this socket initially; use REST. Unsupported/malformed commands -> system.error; no operation succeeds from receipt alone.

Event envelope: {"eventId":"UUID","protocolVersion":"1.5.0","timestamp":"RFC3339 UTC","sequence":1,"type":"task.created","taskId":"UUID","payload":{Task}}. taskId nullable for system events. task.created/task.started/task.cancel_requested/task.completed/task.failed/task.cancelled/task.timed_out carry a full Task. task.progress reserved until measurable progress exists. Control frames use sequence 0 and are not replayed; lifecycle and announcement journal events advance sequence. Deduplicate eventId; process replay by increasing sequence. Disconnect does not cancel tasks. Retry connection with jittered exponential delay 1..30s; stop on 401 until reauthenticated. Reconnect requests events.resume with last applied sequence. On server restart or retention gap replace state; process-local tasks/history are lost on restart in initial release. Fetch snapshot before reconnect subscription or after reset; merge events by updatedAt and terminal-state immutability. Server snapshot/control and live sends are serialized; client must buffer live events during synchronization. Retention bounded and capability advertised. Use WebSocket ping/pong for liveness; no success inference from ping.

## Conversation / voice compatibility
Continue using existing /ws/jarvis for conversation: CHAT_RESUME, CHAT_CANCEL and CHAT_STEER remain legacy commands with legacy seq frames; do not mix envelope versions. Background tasks use independent generated conversation IDs. The process-local Model Gateway defaults to four inference requests with one reserved interactive slot and at most three background leases. Actual Ollama concurrency must be configured/verified separately. Latest physical target: stable 24576 per slot. A reserved lease does not reserve GPU compute and cannot preempt running prompt processing or generation.
Existing GET /api/v1/voice/status advertises STT/TTS. POST /api/v1/voice/transcribe?fileName=recording.wav consumes raw WAV bytes and returns {"text":"..."}; POST /api/v1/voice/speak {"text":"..."} returns audio/wav. Provider unavailable returns 503 {"error":"..."}. Initial companion does not accept binary audio WebSocket frames or claim streaming STT. Client uses push-to-talk/VAD, sends completed recording, streams chat through legacy channel, and requests TTS per complete sentence. Client owns playback queue and echo prevention; on barge-in stop audio, discard queued sentences, and send legacy CHAT_CANCEL. No microphone recording before explicit opt-in. Wake word runs locally if enabled. voice.state values reserved: IDLE, LISTENING, TRANSCRIBING, THINKING, SPEAKING, INTERRUPTED, MUTED, ERROR. Only advertise server streaming after provider support is verified and contract extended.

## Reserved event families
assistant.state (IDLE/THINKING/SPEAKING/ERROR), assistant.message.delta, assistant.message.completed, voice.state, memory.updated, proactive.message are reserved, not yet emitted by companion. Future payload schemas require an additive contract version before integration. No raw secrets, memory contents or internal reasoning in telemetry.

## Task announcements (1.5.0)
assistant.task.announcement carries {"taskId":"UUID","kind":"ACKNOWLEDGMENT|PROGRESS|COMPLETED|FAILED","state":"QUEUED|RUNNING|COMPLETED|FAILED","text":"deterministic state text"}. It uses no LLM, cached personality generation or tool calls. Text is emitted only for the matching actual state. Lifecycle events remain authoritative. PROGRESS describes task.started, never a percentage. Announcements share owner scope, journal sequence and replay semantics. `jarvis.companion.announcements.enabled` controls emission and now defaults true. Windows must deduplicate reconnect events and avoid speaking an equivalent main DELEGATED receipt and task-created announcement twice. No microphone/voice-streaming change.

## Integration provider marker
Capabilities may include providerMode=LIVE or SIMULATED. The isolated integration launcher reports SIMULATED; clients should visibly identify simulated inference even though backend task states are real.

## Dynamic task plans (1.4.0, additive)
Capabilities: taskPlans=true, planEvidenceRequired=true; durableHistory is true ONLY when configured persistent storage is active and restart recovery completes. /state and system.snapshot add plans: [Plan] under the SAME atomic latestSequence cursor as tasks. GET /tasks/{taskId}/plan returns the current Plan, or 404. No plan is mandatory for simple chat. /tasks/{taskId}/plan/revisions returns retained immutable plan revisions (at most 200 per plan), owner-scoped.

Exact events: task.plan.created, task.plan.updated, task.plan.step.updated, task.plan.completed. Each payload is a FULL legacy Task object at its root, PLUS plan: Plan. This intentionally preserves older clients that parse every task.* payload as a Task. Event taskId must equal payload.taskId and payload.plan.taskId. Envelope and replay semantics are unchanged. Plan has planId, taskId, revision, title, createdAt, updatedAt, status (ACTIVE/COMPLETED/CANCELLED/FAILED/INTERRUPTED), steps, completedStepCount and totalStepCount. Step has stepId, title, nullable description, zero-based position, status, nullable startedAt/completedAt/resultSummary/error/evidenceRef. See exact versioned schemas. No percentage is derived from step counts; Task.progress stays null unless actually measured. Plan text must describe actionable user-facing work; hidden reasoning/prompts/secrets are prohibited.

Logical tools plan_create/get/add_step/update_step/reorder/complete map to native taskplan__create/get/add_step/update_step/reorder/complete using the existing native registry. Owner and current task are bound by backend execution context, never accepted from model arguments. Mutations require expectedRevision; stale revisions fail without side effects. CREATE cannot replace an existing plan. REORDER must name every step exactly once; COMPLETED/SKIPPED/CANCELLED steps cannot change status. Allowed transitions: PENDING -> IN_PROGRESS|SKIPPED|CANCELLED; IN_PROGRESS -> COMPLETED|FAILED|SKIPPED|CANCELLED. FAILED -> IN_PROGRESS is an explicit retry transition while its task remains active; it preserves the failed revision and requires fresh post-retry evidence. This metadata transition never reruns a tool or external effect automatically. COMPLETED requires a successful backend-issued tool receipt from the same owner/task; planning calls and model-written evidence strings cannot issue receipts. Backend receipts link tool name/operation/time, never arguments, prompts or raw outputs. A tool receipt proves execution success, not arbitrary semantic claims; step descriptions/results must still be grounded. A final report-only step can remain outside the executable plan. plan_complete requires all steps COMPLETED or SKIPPED; skipped steps require a reason. Plan completion is backend validation, not model assertion.

Every mutation increments revision. Consumers deduplicate eventId, enforce sequence, and reject plan revisions <= the applied revision; a sequence gap requires state.sync. Full snapshot includes all retained current plans and its atomic cursor, so reconnect never depends on receiving every plan delta. Terminal task cancellation/timeouts cancel unfinished steps; further mutations are rejected once task state is not RUNNING/QUEUED. Plan revisions remain auditable. A successful response with unfinished/unverified executable steps fails the task rather than claiming success.

## Durable history and deletion (1.4.0)
Storage is configurable, uses an isolated SQLite history database when enabled, and does not replace existing SQLite conversation or knowledge storage. No request is automatically replayed after restart. QUEUED/RUNNING/CANCEL_REQUESTED history is reconciled to FAILED with a restart interruption error; unfinished plans become INTERRUPTED with unfinished steps CANCELLED. Existing completed/failed/cancelled/timed-out history is retained. New serverInstanceId and process-local event sequence require a full snapshot after restart; the event journal itself is not durable.

DELETE /tasks/{taskId} deletes an owned terminal task, its plan/revisions and execution receipts; 204 on deletion, 404 for unknown/other owner, 409 for active tasks. task.history.deleted carries a full Task-shaped tombstone with result/error cleared so older task.* parsers remain valid; 1.4 clients remove that task/plan. Older clients learn deletion on the next snapshot. Bounded history and configurable terminal retention (default 30 days / 1000 tasks) apply to the same records. Retention never deletes active work. Delete operations never undo external side effects.

## Opt-in autonomous semantic memory (1.4.0)
Full backend only: GET /api/v1/memory/autonomous lists owned non-expired entries (including explicit CONFLICT/PENDING_REVIEW states, not assumed facts); GET /api/v1/memory/autonomous/status reports extractionEnabled/durableMemory/storageNamespace. PUT /api/v1/memory/autonomous/{id} with {"expectedRevision":1,"content":"user-confirmed fact"} performs an explicit revision-checked update/conflict resolution. DELETE the same path returns 204 and deletes related conflicting variants. Unknown/other-owner IDs return 404; stale update is 409; unsafe content is 400. See memory.schema.json. No memory events are emitted yet; memory.updated remains reserved.

Extraction and dreaming default OFF independently. Relevance is determined by structured semantic model output, not keywords. Credential/PII patterns are only deny guards; sensitive/uncertain model classifications are refused. Duplicate canonical facts merge source references; contradictions do not overwrite facts, and require user review. Deletion stores content-free fact-key tombstones and a source-time cutoff so queued old extraction and idle work cannot resurrect deleted records. Restoring a deleted fact requires a future explicit restore feature; automatic extraction will not do it. SQLite support is optional; no existing semantic/knowledge store is replaced, and PostgreSQL/pgvector remains optional future infrastructure work.


## Phase 2 activity and async delegation (1.5.0)

- Capabilities add inferenceTelemetry, asyncDelegation and taskInstructions. Existing fields and activeProcesses semantics remain.
- Task adds nullable conversationId (source chat) and executionConversationId (isolated execution). REST-created tasks without a source chat and old history may have null source links. Results remain in task.completed.payload.result / task history; Windows should render them in the linked surface.
- Main native tools companion__submit/get/cancel/instruct use server-bound owner identity. Successful submission of ALL requested independent tasks ends the conversational loop with deterministic receipt text and terminationReason DELEGATED, completed=false, goalSatisfied=false. A request for three agents must produce three distinct backend taskIds in the same chat turn before acknowledgment; submissions may span native model rounds. The first receipt alone does not end a multi-agent request. Core returns without waiting for task completion. Exact retries are deduplicated by owner plus chat-request key, role and message; different goals in the same request remain separate tasks. Partial submission is not reported as full delegation. Existing agent__run remains synchronous. The native submission key is internal, not a new public REST retry guarantee.
- POST /tasks/{taskId}/instructions accepts {"message":"Additional instruction"}, 1..4000 characters, at most 16 queued instructions. It returns the current Task. Delivery is cooperative at a model-round boundary or a follow-up turn. A late/finalized/terminal task returns 409, full mailbox 429. Journal event task.instruction.accepted has {taskId,delivery:"NEXT_MODEL_ROUND"}; no instruction text is echoed in telemetry.
- /state and system.snapshot add optional metrics. Subscribed sockets emit system.metrics with sequence=0 approximately once a second. It is transient, not journaled, and does not advance the replay cursor. Ignore unknown fields/events but do not drop these control frames because sequence is 0.
- Owner work metrics: activeCompanionTasks, activeCodingTasks, activeTasks (sum of running work), activeSynchronousAgents, activeAgents (running tasks plus helpers), queuedTasks (Companion queue), activeToolExecutions, inferenceActive, inferenceQueued. Coding-specific persistent lifecycle and WAITING_FOR_USER remain in existing CODING_TASK_* events.
- Process-wide gateway metrics: gatewaySlotsInUse, gatewaySlotsConfigured, reservedInteractive, backgroundSubmitSpacingMs, capacityScope=PROCESS. The work lists are owner-filtered; do not mix owner inference counts and process occupancy. ADMITTED means a lease/transport is active, not proof of current GPU decoding.
- Requests include inferenceId/requestId, nullable taskId, profileId/model, physicalContext/inputBudget, queueWaitMs/elapsedMs and phase ADMITTED or WAITING_GATEWAY. Optional resources contain measured host RAM/GPU byte values, sample time and status. Unknown/stale values are omitted; Java heap is never VRAM. No activeModels/Whisper allocation/aggregate throughput field is fabricated.
- Legacy OLLAMA_METRICS now also reports native tool-chat completed prompt/generation timings. phaseTimingSource=OLLAMA_FINAL_RESPONSE and phaseTimingsMeasured identify reliable timing. Native missing durations are omitted. Before first output, loading/runtime queue/prefill/transport cannot be reliably separated; do not invent a live PREFILL state or runtime queue duration.

Schemas/examples: schemas/1.5.0. Full coordination, implementation limits, benchmark evidence and rollout: phase2/PHASE2_CORE_COORDINATION.md and phase2/PHASE2_IMPLEMENTATION.md. Physical 24576 is stable across smaller logical agent budgets. Background admission spacing (250 ms default, configurable/disable with 0) is a burst mitigation only, not GPU preemption or a qualified optimal latency setting.

## Change log
1.5.0: real async delegation, isolated execution/source conversation links, cooperative instructions, deterministic state announcements, independent activity/inference counters and transient system.metrics; stable model-aware contexts and completed-phase telemetry. Older schemas remain.
1.4.0: task-scoped revisioned plans, evidence gating, atomic plan snapshots, optional durable recovery/retention/deletion, additive capabilities and legacy-shaped plan event payloads. Historical 1.3.0 schemas retained.

1.3.0: additive assistant.task.announcement and payload schema. No breaking changes.

1.2.0: additive atomic latestSequence cursor in /state and system.snapshot. After replacing state, resume/poll from that snapshot cursor.

1.1.0: additive serverInstanceId in system.connected and /state. Send it in events.resume; mismatch forces reset, including when new server sequence overlaps an old cursor. Client must compare instance IDs on every connection, discard old state on change, and request state.sync. Omitted ID remains compatible but cannot detect all restart overlaps. Retention: 512 events per owner; 1000 tasks globally; 128 active tasks globally; 1024 process-local owners. Admission returns 429 at capacity. Invalid task requests return 400. REST /state returns serverInstanceId for polling clients, which must compare it each poll. No automatic eviction of owner journals.


1.0.0: initial additive integration target; legacy APIs unchanged. Streaming voice, durable history, automatic memory and proactive features are not promised by this release.
